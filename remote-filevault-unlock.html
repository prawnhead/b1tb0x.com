Remote FileVault unlock over SSH

A FileVault-encrypted Mac that reboots stops at a pre-boot screen and waits for someone to unlock the disk before it can finish starting. On an Apple Silicon Mac with Remote Login enabled, you can do that unlock over SSH — no monitor, no keyboard, no one standing at the machine. This is how, and how to reach it remotely across a VPN.

why a reboot leaves it stuck

When FileVault is on, the system disk is encrypted. After a reboot the Mac can start the firmware and a minimal pre-boot environment, but it cannot mount the real system volume until the disk is unlocked with a local account's credentials. Until then the full OS — and anything that depends on it, including any VPN client — is not running.

the mechanism

On Apple Silicon Macs, when Remote Login (SSH) is enabled, macOS automatically brings up a minimal SSH listener in that pre-boot environment after any restart. You do not need to arm it per-reboot (the old fdesetup authrestart step from Intel/T2 machines no longer applies). You connect, authenticate with a local account, the disk unlocks, that minimal session closes, and the Mac continues to a normal boot where SSH works as usual.

# from a machine on the same local network as the Mac
ssh user@<mac-local-ip>

This system is locked. To unlock it, use a local
account name and password.
(user@<mac-local-ip>) Password:
System successfully unlocked.
You may now use SSH to authenticate normally.

The connection then closes on its own — that is expected. Wait ~30–60 s for the Mac to finish booting, then SSH in normally.

the catch: a VPN can't reach the pre-boot stage

The pre-boot listener runs before the OS is up, so no VPN daemon is running — a mesh-VPN address or hostname for the Mac is dead until after you have already unlocked it. The pre-boot environment only brings up base networking (wired DHCP → a local IP) and answers SSH on that local address.

So you can only reach the unlock prompt over the local network. If you are off-site, you reach that local network through a jump host: any always-on machine on the same LAN that you can get to over your VPN.

# reach the LAN via an always-on relay, then unlock the Mac by its local IP
ssh -J user@relay-host user@<mac-local-ip>
Make the relay a plain, unencrypted Linux box. If your relay is itself an encrypted Mac, a power failure leaves it sitting at the same locked pre-boot screen — chicken and egg. A small Linux host (a Pi, a NAS, a hypervisor) with no full-disk encryption boots unattended straight to a working SSH and VPN, so it is always there to jump through.

surviving a power failure, not just a reboot

For this to work after the power goes out and comes back, two things must be true:

  • The Mac must power itself back on. Apple Silicon Macs restore their previous power state after power is restored; the control is System Settings → Energy → "Start up when power is connected", set to Always. (The legacy pmset autorestart flag does not govern this on Apple Silicon — don't trust it.)
  • The relay must come back on its own — unencrypted and set to auto-boot, so it is reachable while the Mac waits locked.

recovery checklist

  1. Remote Login (SSH) enabled on each Mac.
  2. Each Mac set to start up automatically when power is connected.
  3. At least one always-on, unencrypted Linux box on the LAN, reachable over your VPN.
  4. Know each Mac's local IP at the pre-boot stage (normally its usual wired DHCP address — confirm it, since the unlock target depends on it).
  5. After an outage: VPN → relay → ssh user@<mac-local-ip> → enter a local password → wait → reconnect normally.
